## Exact cause and matching crash addresses

The old state allocator requested `Exe.Allocate(0x5000, 0x1000)` indirectly.
The returned **virtual** address was `0x01E5F400`; requesting allocator alignment
did not establish VA page alignment. The two native prologue trampolines occupy
`0x01E5F000` and `0x01E5F010`, on the same page as the state buffer's first byte.

The real emitted owner at `0x01E66410` executes:

~~~asm
01E66498  57                   push edi              ; off item
01E66499  53                   push ebx              ; main item
01E6649A  8B CE                mov ecx, esi          ; actor
01E6649C  E8 5F 8B FF FF       call 01E5F000
01E664A1  8B 9E 40 04 00 00    mov ebx, [esi+440h]   ; reported return address
...
01E664BE  6A 04                push 4                ; PAGE_READWRITE
01E664C0  68 00 50 00 00       push 5000h
01E664C5  68 00 F4 E5 01       push 01E5F400h
01E664CA  FF 15 08 13 FC 00    call dword ptr [00FC1308h] ; VirtualProtect IAT
~~~

The requested bytes `[0x01E5F400, 0x01E64400)` touch all pages in
`[0x01E5F000, 0x01E65000)`. Windows applies protection to all touched pages;
`PAGE_READWRITE` does not permit instruction execution under DEP.
The client has `IMAGE_DLLCHARACTERISTICS_NX_COMPAT` set. These are the documented
[VirtualProtect range semantics](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualprotect)
and [memory protection constants](https://learn.microsoft.com/en-us/windows/win32/memory/memory-protection-constants).

Thus the first native call can succeed, cold initialization removes EXECUTE,
and the next call faults on the first instruction at `0x01E5F000`, leaving
`0x01E664A1` as its return address. The posted EBX=EDI=0 is consistent with an
empty-equipment call; an empty call is sufficient to reproduce the failure.
The draw trampoline is affected by the same protection error.

This cause is independent of weapon ACT x/y, angles, selected frames or Lua
fallback names. Those cannot correct an instruction-fetch protection fault.

## Fix and updated bytes

`allocateStatePages` reserves `size + 0xFFF` bytes and aligns the **returned VA**
up to 0x1000, applying identical padding to its physical address. The entire
reservation stays owned, including padding. No subsequent allocation can share
any protected state page. The owner emitter rejects an unaligned protected
range or a range overlapping its trampoline. PAGE_READWRITE remains unchanged.

| Field | Crashing binary | Replacement |
|---|---|---|
| State VA | `0x01E5F400` | `0x01E60000` |
| Protected pages, end exclusive | `[0x01E5F000,0x01E65000)` | `[0x01E60000,0x01E65000)` |
| Actor row table | `0x01E60400` | `0x01E61000` |
| Item view table | `0x01E5F800` | `0x01E60400` |
| Bytes at `0x01E664C5` | `68 00 F4 E5 01` | `68 00 00 E6 01` |
| State-ready comparison at `0x01E664AD` | `83 3D 00 F4 E5 01 01` | `83 3D 00 00 E6 01 01` |
| Registry address at `0x01E664EF` | `05 00 04 E6 01` | `05 00 10 E6 01` |

All state references are regenerated by QJS; this is not a one-immediate hotfix.
The four native entry-hook bytes and code cave addresses happen to remain the
same in this rebuild. The full owner, compositor, legacy core and depth helper
are compared against their relocated source payloads. The DWCP payload did not
need a code change for this allocation fault.

A separate PE header defect was repaired: WARP left `SizeOfHeaders=0x400` while
the tenth section header ends at file offset `0x408`. The builder now writes
`0x600`, verifies that the complete table is covered, and checks it fits before
the first section's raw data. This is a distinct structural fix; it is not
claimed as the cause of the posted crash. Existing mapped bytes outside the
four intended hook regions remain identical to the saved pre-dual baseline.

## Reproduction and validation boundary

[The executable regression](../tools/verify_dual_weapon_page_protection.py)
maps each actual PE section with its permissions and executes the installed
entry, emitted equipment owner and genuine five-byte prologue plus jump.
Its VirtualProtect stub applies Windows page rounding and enforces NX.
Only the native equipment/resource function bodies are ABI stubs.

[Machine-readable result](evidence/dual-weapon-page-protection-20260905.json):

- Archived binary: first empty call returns; second raises `UC_ERR_FETCH_PROT`
  at `0x01E5F000`, stack return `0x01E664A1` — both match the user's crash log.
- Replacement: eight transitions complete, including empty twice, main-only,
  off-only, dagger/dagger, sword/dagger, dagger/sword, then unequip. All 19 native
  calls traverse the actual trampoline. State starts at zero, VirtualProtect
  executes once, and subsequent state writes occur on writable, non-executable
  pages while both trampolines and all checked code retain EXECUTE.
- Correct stock capture/restore sequence, actor main/off state, callee-save
  registers and RET 8 stack cleanup are checked on each completed transition.
- The allocator regression tests every VA page residue, including 0x400,
  and verifies that both leading/trailing padding remain reserved.

The earlier owner harness set state-ready=1 and replaced the trampoline with a
RET 8 stub. It proved resource lifetime/ABI properties but could not detect
this initialization error. That limitation is now explicit in its report.
No earlier packet-emulation result constitutes live crash-free or visual
acceptance. Dagger/dagger coordinates and off-hand placement still require the
user's in-game check of this replacement.
