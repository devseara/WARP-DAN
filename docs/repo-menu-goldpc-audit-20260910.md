# Repository menu and Gold PC Cafe audit — 2026-09-10

Audited WARP revision `77c1dde1dce5c6d4bca8f9cc6a89dab908324cd0` and the local
`../BanquetOfHeroes` server sources. The supplied EXE's immediate crash was
already isolated in [the incident diagnosis](louis-hide-buttons-crash-20260910.md).
This audit confirms the callback defect can be generated by the current repo.
The Gold PC Cafe disconnect has a separate, confirmed packet-width cause.

## 1. Auto Hunt / AutoSupport callbacks survive their owning code

Severity: P1. Confirmed with this repository's `win32/WARP_console.exe`, using
a clean 2025-07-16 client and an isolated copy of the current patch sources.

`ROGlobalZeroMenu.qjs:2290` and `:2356` embed direct CALLs to the cached Auto
Hunt and AutoSupport request callbacks. Reapplying a producer allocates new
callbacks, but neither producer refreshes the menu's emitted CALL operands.
There are no cleanup/rebuild hooks for these dependencies. Integer checks on
CACHE fields at menu construction establish address shape, not ownership or
liveness. `CACHE.put` does not update references already emitted into an EXE.

AutoSupport's route-cell update at `AutoSupportUI.qjs:7167` does not repair
this: the AutoSupport mouse-up handler calls a fixed target instead of loading
the route cell. Auto Hunt has no equivalent menu route-cell refresh.

The six real-WARP cases produced these results:

| Case | Exported PE result |
| --- | --- |
| Fresh feature/menu build | All three custom callbacks valid |
| Hide native buttons and show custom buttons, without rebuilding producers | All three custom callbacks remain valid |
| Hide custom buttons, then regenerate the menu | AutoSupport and Item Collection published visibility resets to 1 |
| Disable/reapply AutoCombatUI | Auto Hunt still calls its cleared old callback |
| Disable/reapply AutoSupportUI | AutoSupport still calls its cleared old callback |
| Disable/reapply both | Both custom buttons still call cleared old callbacks |

For the combined reapply case, Auto Hunt retains `0x01884C80` while its new
callback is `0x01D6DED0`; AutoSupport retains `0x01A83E90` while its new
callback is `0x0216C600`. Both old entries contain zero bytes in the exported
EXE. This reproduces the same defect as the supplied crashing client, whose
allocation addresses differ with its larger patch set.

The regression uses WARP's ordinary profile application, then real
`SetActivePatch`, `ClearPatch`, and patch functions for the later actions.
The probe is registered after the production patches in the catalog because
WARP applies catalog order, not arbitrary ordering in the profile list.
It checks the currently hooked menu generation, rather than treating unused
older allocation bytes as live code.

Two earlier probe-development outputs are not acceptance evidence. The final
matrix is under `Outputs/menu_lifecycle_ordered_20260910`; the checked-in
[summary](evidence/menu-lifecycle-20260910.json) records the six final cases,
EXE hashes, repository revision, and source hashes.

Reproduce with a fresh output directory:

```powershell
.\.venv\Scripts\python.exe tools\verify_menu_patch_lifecycle.py --source '2025-07-16_Ragexe_175220998_clientinfo\2025-07-16_Ragexe_175220998_clientinfo.exe' --output Outputs\menu-lifecycle-audit
```

On this revision, exit code 1 is expected: the test detects the three callback
failures and the visibility reset. These are emitted-code checks; they do not
claim live screenshot acceptance or complete menu layout coverage.

A durable fix needs consumer rebuilding or stable callback/state ownership,
including the AutoSupport-to-AutoCombat peer references. Editing only the two
CALL operands would leave the broader dependency lifetime unchecked.

## 2. Menu regeneration resets visibility and splits AutoSupport ownership

Severity: P2. `ROGlobalZeroMenu.qjs:2081` and `:2112` initialize Item Collection
and AutoSupport's menu visibility cells to 1 without preserving the pending
hide selection. The real-WARP hidden-before-regeneration case exported 0 for
Auto Hunt but 1 for both other published visibility cells.

AutoSupport also captures `autoSupportVisibleVir` at line 2105 before moving
its bridge to the new menu cell at lines 2113-2115. Its sync and row-count code
uses the captured address at lines 2377 and 2436, whereas later hide/show
writes target the newly published cell. The renderer and the writer can
therefore disagree about which value owns visibility. Fixing the initialization
alone does not fix this address split.

## 3. Gold PC Cafe 0x0A16 is accidentally widened by NAME_LENGTH

Severity: P1. This is a protocol mismatch related to extended names, separate
from the menu callback crash.

The supplied EXE's function at `0x00914DA0` constructs
`CZ_DYNAMICNPC_CREATE_REQUEST` (`0x0A16`):

- `0x00914DCF`: PUSH 0x18, a 24-byte string buffer.
- Fixed identifier at `0x0103AA6C`: `GOLDPCCAFE`.
- `0x00914DF2`: PUSH 0x1A, a 26-byte send length.
- `0x00914DF6`: CALL `0x00C14920`, the send path.
- The packet registration at `0x00AA4847` also declares 26 bytes.

The whole native sender and the packet registration match the clean client
byte-for-byte. Emulating the actual sender with string/network services
stubbed captures exactly:

```text
16 0A 47 4F 4C 44 50 43 43 41 46 45 00 00 00 00 00 00 00 00 00 00 00 00 00 00
```

The [packet evidence](evidence/goldpc-packet-20260910.json) records the result.
No network traffic was generated.

In the local server:

- `src/common/mmo.hpp:167` defines `NAME_LENGTH` as `(127 + 1)`.
- `src/map/packets_struct.hpp:5791` declares the packed request as a uint16
  opcode followed by `char name[NAME_LENGTH]`: 2 + 128 = 130 bytes.
- `src/map/clif_packetdb.hpp:2108` registers the request using `sizeof`.
- `src/map/clif.cpp:28716` disconnects when fewer than that length remain.
- `clif_parse_dynamic_npc` at line 27469 only accepts the fixed `GOLDPCCAFE`
  identifier and maps it to the `PLAYTIMEPOINTS` NPC script.

The supplied warning's 130 expected / 26 available values therefore match
this exact discrepancy. The NPC handler is never reached on that request.
This field identifies a native NPC action; it is not a player display name.

The narrow server correction is to keep this wire identifier at 24 bytes,
independent of extended character-name storage, and assert the packed request
size is 26. For example:

```cpp
struct PACKET_CZ_DYNAMICNPC_CREATE_REQUEST {
    uint16 PacketType;
    char name[24]; // Fixed client NPC identifier, including NUL.
} __attribute__((packed));
static_assert(sizeof(PACKET_CZ_DYNAMICNPC_CREATE_REQUEST) == 26);
```

An explicitly named 24-byte wire-identifier constant would also be suitable.
Changing global NAME_LENGTH or merely suppressing the disconnect would not
correct the protocol definition. This audit read the local server sources;
it did not inspect or change the running server binary.

No production QJS, server source, deployed EXE, or running server was modified.
